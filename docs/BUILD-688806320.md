# Build `288.6.8.8_user_688806320` — verification record

This build is accepted by the guard alongside the original
`288.6.8.8_user_688805020`. It was **not** re-tested by the maintainer on
hardware; the port and the hardware report come from
[@mhabou](https://github.com/mhabou) (issue #1). Everything below is what was
checked locally, and what was not.

## The five addresses

They are read from the extracted ELF, not copied from the other build:

```
$ llvm-nm --defined-only firmware/kernel-688806320.elf | grep -E 'prepare_kernel_cred|def_chr_fops|ashmem_fops|sel_read_enforce'
c0077c3c T prepare_kernel_cred
c0724f18 T def_chr_fops
c075fac0 t ashmem_fops
c0245050 t sel_read_enforce

$ python scripts/find_misc_fops.py ashmem --kernel firmware/kernel-688806320.elf
ashmem         misc=0xc0a137ac minor=255 (dynamic) fops=0xc075fac0
               fops field to overwrite: 0xc0a137b4
```

`selinux_enforcing` is not exported in kallsyms; its address is decoded from
the `sel_read_enforce` prologue, which loads it with `movw/movt`:

```
c0245068: e306c6f0  movw  r12, #0x66f0
c024506c: e34cc0ac  movt  r12, #0xc0ac      -> 0xc0ac66f0
```

| Symbol | Address | Used for |
|---|---|---|
| `prepare_kernel_cred` | `0xc0077c3c` | new kernel cred |
| `selinux_enforcing` | `0xc0ac66f0` | set to 0 |
| `def_chr_fops` | `0xc0724f18` | neutralize the fake fd |
| `ashmem_misc.fops` | `0xc0a137b4` | controlled 4-byte write target |
| `ashmem_fops` | `0xc075fac0` | original pointer restored by the payload |

All five are **identical** to the 688805020 values, which is why
`probes/gl_exploit.c` needs no per-build address table — only the banner
check differs, and both images report `3.10.54+`.

> The equality of the addresses is a property of these two images, not a
> general rule. A further OTA must be verified from scratch; never assume the
> table carries over.

## What is verified, and what is not

Verified locally:

- the OTA is the expected public package and its kernel banner is `3.10.54+`;
- the five addresses above resolve in the extracted ELF;
- the guard accepts exactly the two supported incrementals
  (`tests/`), and rejects anything else before pushing the payload;
- `fetch_boot.py --build` selects the right OTA and writes
  `<build>`-suffixed artifacts without overwriting the other build.

Not verified:

- hardware success rate on 688806320 (the maintainer only ran the reliability
  campaign on 688805020);
- behaviour of later OTAs (addresses or the PI-futex bug may change);
- `panic_on_oops` / SELinux defaults on a 688806320 unit — `gl_bench.py doctor`
  reports them before any attempt.

Only the hardware report in issue #1 supports 688806320. Treat the ~2 % panic
figure as an extrapolation, not a measurement.
